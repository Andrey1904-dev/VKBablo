# VK AI Manager

Автономная платформа управления четырьмя сообществами ВКонтакте: генерация текстов и изображений, **обязательное ручное одобрение**, отложенная публикация по московскому расписанию.

> **Дизайн.** Интерфейс переведён на дизайн-систему **DesignVK** («VKBablo Premium»):
> тёмная тема по умолчанию и светлая, шрифты Inter + JetBrains Mono, фиолетовый акцент
> `#8B5CF6`, фирменные карточки, таймлайн «Сегодня», сплит-просмотр «На проверке»,
> модальное окно «Создать публикацию», тосты, адаптив от 320px. Вся функциональность
> (авторизация, Supabase/`getBackend()`, одобрение постов, календарь, студия, персонажи,
> аналитика, настройки, уведомления) сохранена.

Сообщества:

1. **Ну и история**
2. **Милана и её деревенский гламур**
3. **ВСЯ СУТЬ ЖИЗНИ**
4. **Вероника в поиске настоящего мужчины**

Слоты по умолчанию для каждой группы: **13:30, 17:30, 21:30 Europe/Moscow**. Расписание можно изменить в карточке сообщества.

Без явного одобрения конкретной версии поста отправка в VK **технически невозможна** (проверка на сервере, не только в UI).

## Что уже работает локально

- Закрытый вход / первый запуск (создание владельца)
- Панель, четыре сообщества, публикации, календарь, ИИ-студия, персонажи, аналитика, настройки, уведомления
- Очередь генерации, статусы, версии, сброс одобрения после правки текста/картинки/времени/группы
- Тестовый AI-движок (без внешних ключей) и адаптеры OpenAI / совместимого API
- VK **dry-run** в режиме «Тестирование»: посты не уходят в VK
- Глобальная кнопка «Стоп» для автоматизации
- Шифрование VK/AI секретов, журнал действий, лимит расходов AI

## Что требует внешних ключей

| Функция | Что нужно | Статус без ключа |
|---|---|---|
| Боевой текст/картинка GPT, DALL·E и т.п. | AI API key в настройках | Тестовый движок |
| Реальная отложенная запись VK | токен сообщества + Group ID, режим «С согласованием» | Имитация, статус `test_…` |
| Облачная БД, Storage, Auth, Realtime | проект Supabase | Локальная SQLite + файлы |
| Публикация сайта | GitHub Pages (Actions) | Готово после настройки workflow |
| Telegram / Web Push | не подключены | Заложено в архитектуре |

Не утверждается, что VK-публикация или облако работают, пока вы не задали секреты.

## Быстрый старт

```bash
npm install
cp .env.example .env
npm run dev
```

- UI: http://localhost:5173
- API: http://localhost:8787

В локальном Node/SQLite режиме первый владелец создаётся при первом запуске UI (или через локальные `BOOTSTRAP_*` env). В Supabase-режиме браузерная регистрация отключена: первый владелец создаётся только операторским CLI `node scripts/bootstrap-owner.mjs` после применения миграций и серверной настройки `OWNER_SETUP_SECRET`; см. `CODEX_SETUP.md`. **Не присылайте пароли, токены или setup secret в чат.**

Затем на главной: **Подготовить ближайшие слоты**. Посты появятся со статусом «На проверке».

```bash
npm test
```

Проверяют: запрет публикации без одобрения, сброс согласования после правки, dry-run планирования, слоты Москвы, идемпотентность слота.

## Режимы

1. **Тестирование** (по умолчанию) — генерация, очередь, согласование, имитация VK.
2. **С согласованием** — только в облачном Supabase backend при `app_mode=approval`, `real_publish_enabled=true`, валидном VK подключении и одобрении текущего hash.
3. Local Node/SQLite принудительно остаётся test/dry-run; он не подключает VK и не хранит VK-токены. Автопубликация без одобрения **не реализована как рабочий режим**.

## Supabase

Производственное хранилище: PostgreSQL, Storage, Auth, Realtime.

Пошагово: [`supabase/README.md`](supabase/README.md)

Секреты только в `.env` (локальный стенд) или в секретах Edge Functions (Supabase) — никогда в коде, Git и чате:

- `SUPABASE_URL`
- `SUPABASE_ANON_KEY` (и `VITE_SUPABASE_ANON_KEY` для Realtime на клиенте)
- `SUPABASE_SERVICE_ROLE_KEY` — **только сервер**, никогда в браузер и никогда в чат

Пока service role не задан, сервер честно работает на локальной SQLite и показывает баннер в панели.

## Деплой: GitHub Pages + Supabase

Cloudflare в проекте не используется (ни Workers, ни D1/R2, ни Wrangler).

1. **Фронтенд** — GitHub Actions собирает Vite и публикует `dist` на GitHub Pages
   (hash-роутинг, `VITE_BASE`). Без GitHub Actions variables сборка остаётся demo; для облачного
   backend задаются только публичные repository Variables `VITE_SUPABASE_URL`,
   `VITE_SUPABASE_ANON_KEY` и `VITE_BACKEND_MODE=auto`.
2. **Серверная часть** — Supabase: миграции, RLS, Storage, Auth, Edge Functions и Cron.
3. **Долгие задачи** (генерация, публикация, статистика) выполняются очередями и воркером,
   а не внутри одного HTTP-запроса: у Edge Functions есть лимит времени выполнения.

Пошагово: [`CODEX_SETUP.md`](CODEX_SETUP.md) · детали схемы: [`supabase/README.md`](supabase/README.md)

## Безопасность

- Сессия в httpOnly cookie, проверка Origin на мутациях
- VK-токены шифруются AES-256-GCM, API их не возвращает
- RLS в Supabase, отдельная таблица `community_secrets` без политик для `authenticated`
- Storage bucket `media` приватный, просмотр через signed URL; загрузка создаёт UUID-путь без перезаписи
- Платные AI-вызовы в dry-run запрещены; в Supabase требуют явного флага и транзакционного reservation/settlement бюджета (миграция `20261015100000`)
- Service role не заменяет проверку сессии пользователя
