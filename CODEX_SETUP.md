# Подключение VKBablo через Codex

> **Безопасный режим по умолчанию.** Не отправляйте ключи, пароли, токены, Supabase service-role key или `OWNER_SETUP_SECRET` в чат, GitHub issue, коммит или клиентский код. Переменные `VITE_*` попадают в браузерный JavaScript. Пока всё не проверено на отдельном тестовом контуре, не включайте реальные VK-публикации и платные AI-вызовы.

## 1. Локальная проверка

```bash
git clone https://github.com/Andrey1904-dev/VKBablo.git
cd VKBablo
npm ci
npm run typecheck
npm test
npm run build
npm run build:pages
```

Для локального стенда используйте `.env.example` как шаблон, храните `.env` только локально (он игнорируется Git) и запускайте `npm run dev`. Локальный first-owner bootstrap через `BOOTSTRAP_EMAIL` / `BOOTSTRAP_PASSWORD` относится только к Node/SQLite стенду; эти значения не нужны для Supabase. Не подменяйте этим проверку облачного режима.

Перед любыми изменениями сверяйтесь с `HANDOFF.md`, действующими миграциями, RLS и тестами. Сохраняйте существующую React/TypeScript/Vite + Supabase архитектуру. Cloudflare не используется.

## 2. Supabase: подготовка и проверка

1. Создайте отдельный тестовый Supabase project. Production-проект пока не подключайте.
2. Установите Supabase CLI по официальной инструкции и войдите интерактивно (`supabase login`). Не записывайте токен входа в репозиторий.
3. Изучите все файлы `supabase/migrations` и настройки `supabase/config.toml`. Применяйте миграции сначала только к тестовому проекту; перед `supabase db push` просмотрите план и убедитесь, что целевой project ref верный.
4. Примените миграции в последовательности CLI. Миграция `20261014120800_owner_bootstrap_safety.sql` меняет роль по умолчанию для новых Auth-профилей на `viewer`, создаёт закрытую таблицу one-time bootstrap state и ограничивает promotion до `owner` защищённым серверным RPC. Не редактируйте уже опубликованные/применённые миграции; исправления оформляйте новой миграцией.
5. Разверните `vk-ai-api` и `vk-ai-worker`. Edge Functions, RLS, Auth triggers, Storage, RPC и Cron **не проверены на живом проекте** в рамках текущей работы. Сначала проверьте их на тестовом проекте.
6. Настройте нужные серверные Edge Function secrets в Supabase Dashboard → Edge Functions → Secrets (или через утверждённый оператором CLI-процесс). Значения не храните в Vite variables. `OWNER_SETUP_SECRET` должен содержать случайные 32–256 символов и задаётся только для серверной функции; никогда не кладите его в `VITE_*`, frontend, URL, query string или браузерное хранилище.
7. Отключите публичную саморегистрацию в Supabase Auth. Функция `vk-ai-api` проверяет JWT/операторский секрет самостоятельно; не воспринимайте `verify_jwt = false` как замену этой проверке.

В рамках текущей подготовки **не выполняйте** `supabase link`, `supabase db push`, deployment или реальную настройку проекта без отдельного разрешения владельца. Миграции не применялись.

## 3. Безопасное создание первого владельца в Supabase

Supabase first-owner создаётся только из операторского CLI; форма в браузере намеренно отключена. После применения миграций и развёртывания `vk-ai-api` настройте `OWNER_SETUP_SECRET` в серверных Secrets и запустите из корня репозитория в интерактивном терминале:

```bash
node scripts/bootstrap-owner.mjs
```

Укажите `SUPABASE_URL` и публичный `SUPABASE_ANON_KEY` в окружении оператора (это не service-role key). Скрипт запросит email и имя; пароль владельца и `OWNER_SETUP_SECRET` вводятся без отображения символов. Их можно передать переменными окружения, но не помещайте значения в аргументы командной строки, shell history или `.env` frontend-сборки. Не запускайте этот CLI через браузер или CI-логи.

Серверная функция сравнивает setup secret фиксированным объёмом работы, атомарно резервирует единственный bootstrap в БД, создаёт Auth user через Admin API, фиксирует Auth ID и только затем повышает его профиль до `owner`. Повтор с тем же email может продолжить только уже зафиксированную операцию; другая заявка блокируется. Пароль, secret и Auth credentials не возвращаются в ответе или audit log.

**Если CLI сообщил об unknown outcome, timeout, `setup_unknown` или manual recovery:** не запускайте его повторно вслепую и не создавайте вручную второго Auth user. Сверьте Supabase Auth по указанному email и состояние `public.owner_bootstrap_state` на тестовом проекте; если результат не ясен, остановитесь и передайте администратору. Секрет не сбрасывайте и latch не удаляйте до установления фактического состояния. Обычный успешный запуск завершается сообщением о входе через форму Supabase Auth.

## 4. GitHub Pages и frontend

В настройках GitHub: Settings → Pages → Source: GitHub Actions. Workflow `.github/workflows/pages.yml` собирает demo-версию с hash-router. Для подключения Supabase frontend используйте только публичные `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY` (publishable/anon key), задавая их в защищённых настройках сборки. Повторно проверьте RLS и авторизацию на тестовом проекте.

Запрещено добавлять в frontend/build variables:

- Supabase `service_role` key;
- `OWNER_SETUP_SECRET` или worker secret;
- VK-токены;
- AI API keys, encryption/session secrets или пароли.

## 5. Интеграции и публикации

1. Проверьте `health`, Auth/RLS, роли `owner` / `editor` / `viewer`, Storage и RPC сначала на тестовых аккаунтах и тестовом проекте.
2. Все посты должны оставаться с обязательным ручным одобрением. Любое изменение текста, изображения, сообщества или времени аннулирует старое одобрение.
3. Все проверки VK/AI выполняйте через mock/dry-run. Реальный `wall.post`, загрузку в VK и `wall.delete` не проверяйте до отдельного разрешения.
4. Неизвестный исход VK `wall.post` **не означает**, что публикация не состоялась: автоматический повтор запрещён. Сверьте пост вручную в VK перед любым явным retry. Отмена считается завершённой только после подтверждения `wall.delete` и фиксации результата в БД.
5. Реальные платные AI-вызовы выключены по умолчанию. Не включайте их до проверки тарифов, лимита расходов и конкурентного budget reservation.
6. Сохраните четыре сообщества, расписание 13:30 / 17:30 / 21:30 `Europe/Moscow` и 12 постов/день.

## 6. Проверки перед сдачей изменений

```bash
npm run typecheck
npm test
npm run build
npm run build:pages
node scripts/sync-shared.mjs --check
git diff --check
```

Также выполните `deno check` для обеих Edge Functions при изменении их кода. SQL grammar parsing не проверяет выполнение PL/pgSQL, RLS и транзакции; не называйте миграцию проверенной без PostgreSQL/Supabase-теста. Фиксируйте фактические результаты в `HANDOFF.md`.

- [ ] Diff и секреты проверены; случайные `VITE_*` credentials отсутствуют.
- [ ] Typecheck, тесты и обе сборки выполнены; результаты записаны без выдуманных успехов.
- [ ] Migrations/Edge Functions проверены только на разрешённом тестовом проекте.
- [ ] Одобрение публикаций обязательно, и неодобренные/изменённые посты не публикуются.
- [ ] Нет реальных VK-вызовов, платных AI-вызовов или внешних аккаунтов без отдельного разрешения.
- [ ] Нет автоматического повтора `wall.post` при неизвестном результате.
- [ ] Коммит сделан в текущей рабочей ветке; PR открывается из неё и не сливается без отдельного указания.
